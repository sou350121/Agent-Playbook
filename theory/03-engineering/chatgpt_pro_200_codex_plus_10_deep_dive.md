## 技术架构拆解

### 核心设计决策

- **把额度做成「加权计量单位」而非 token 数**：同一份订阅额度，在不同模型 / 模式下的消耗速率差异极大。这是订阅制能维持固定月费的前提，也是用户无法预先估算成本的根本原因。
- **速度档位按倍率收费**：Fast 模式按标准模式的 2.5 倍速率消耗额度；Ultrafast 模式按 8 倍消耗。官方明确提示「额度翻倍 ≠ 产出翻倍」。
- **Dots 常驻助理独立计量**：深度嵌入工作流的常驻 AI 助理，其延伸调用额度独立运作，不挤占主账号的核心生成算力池。这是把「后台常开 agent」和「前台会话」的成本风险隔离开的设计。
- **支持预付费 credit 兜底**：先用包含额度，再扣 credit 余额；Plus / Pro 用户触及上限后可在不改套餐的前提下购买更多。credit 覆盖 Codex、ChatGPT Work 以及 Office 三件套里的 ChatGPT。
- **订阅之外的旁路**：官方文档说明用户「也可用 API key 运行额外的本地对话，按标准 API 价格计费」。这条旁路是重度用户绕开订阅天花板的官方承认路径。

## 实用评估

### 什么场景值得用

- **常态化 agentic coding**：在 Codex CLI / IDE 里做长任务改代码，订阅制的固定月费比 API 更容易封顶预算，尤其在额度翻倍的窗口期内性价比明显改善。
- **需要云端协作特性的人**：GitHub 代码审查、Slack 集成、云端任务这些特性只在订阅通道上有，API 通道拿不到。
- **把 Dots 当常驻后台 agent 用的团队**：独立计量意味着常驻 agent 不会把主会话额度吃干净，这是架构上比较干净的分舱设计。

### 什么场景不值得用

- **把额度当容量承诺来排产**：这次事件本身就是最好的反例——配额条款可以单方面改，又在舆论压力下改回来。任何写进生产 plan 的「每月可用 N 次」都是不可依赖的。
- **需要可预测 token 成本的多 agent 流水线**：加权计费 + 上下文长度 + 沙箱调用次数叠加，成本方差极大。生产链路应该走 API 并按项目设预算。
- **批量任务开 Fast / Ultrafast**：2.5x / 8x 的倍率会以相同速率烧掉额度，对吞吐优先的批处理没有意义。
- **仅靠 Pro 100 撑高频使用**：据报道 Pro 200 与 Pro 100 的单位价格倍率已趋同，若使用量中等，先测 Pro 100 再决定更划算。

### 迁移成本

- **Pro 100 ↔ Pro 200 切换**：月付制，改套餐在账号设置内完成，判断错误的代价是一个计费周期。
- **订阅 → API 混合路径**：Codex CLI 支持通过 API key 登录（`codex login --with-api-key`），本地会话按标准 API 价计费，但会失去 GitHub 代码审查、Slack、云端任务等 cloud 特性。工作量主要是把 CI 里的 `codex exec` 独立出来、设项目预算、并验证 key 权限。
- **模型降档**：日常任务从旗舰档换到轻量档，配合 `codex -m <model>`，成本可降一半到几十分之一（取决于所选模型档位）。需要重新验证输出质量。

## 对你的意义

对 Ken 这种「VLA 研究 + AI 应用开发」双线跑的人来说，实际的结论有三条：

1. **不要把 agent 额度当基础设施容量**。这次从砍半到翻倍只隔了一个月，说明订阅配额是可协商的市场变量，不是 SLA。任何依赖它的流水线都要有 API 兜底。
2. **加速档位是成本陷阱，不是效率工具**。Ultrafast 的 8x 和其他档位的 2.5x 是官方亲口说的，批量任务开它们纯属烧钱；把规划/硬调试留给强模型、把改名/测试脚手架/文档交给轻量模型，是更稳的分层策略。
3. **上下文卫生直接就是钱**。AGENTS.md 写短、按目录嵌套、关掉本次不用的 MCP server、收窄文件与时间范围——这些不是「好习惯」，是每次调用都在为你省额度。
