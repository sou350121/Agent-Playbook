## ⚡ 快速判斷（30 秒讀完這段就夠了）

- **一句话定位**：揭示 AI 编码从「能写代码」到「能信任代码」之间的验证鸿沟
- **现在值得用吗**：是，但必须建立系统化验证流程
- **适合场景**：已有成熟 review 流程的团队、需要快速原型验证的场景
- **不适合场景**：缺乏代码审查文化、对领域知识理解不足的团队
- **与「技术债务」核心差异**：技术债务是「知道有问题但先欠着」，验证债务是「看起来没问题但其实有隐患」

## 是什么 / 解决什么问题

2026 年的 AI 编码已经跨越了「能不能用」的争论阶段，进入了「怎么用才对」的深水区。当 Claude Code、Cursor、Pi Coding Agent 等工具能够 在 10 分钟内生成一个完整的 PR 时，一个隐蔽的陷阱正在形成：**验证债务（Verification Debt）**。

这个概念由开发者 Lars Janssen 在 2026 年 3 月提出，指的是「我们生成代码的速度」与「我们验证代码的能力」之间不断扩大的差距。每当工程师点击 approve 批准一个自己没有完全理解的 diff 时，就是在向未来借债。

与传统技术债务不同，验证债务的危险性在于它**培养虚假信心**：代码库看起来干净，测试全部通过，PR 描述写得比人类还好——但六个月后你可能发现，团队构建了「规格说明书写的内容」，而不是「客户真正需要的东西」。

这篇文章的核心价值在于：它不是反 AI，而是提醒在 agent 编码成为常态的 2026 年，**验证能力必须与生成能力同步进化**。

## 技术架构拆解

### 核心设计决策

验证债务的产生源于 AI 编码工作流的几个结构性特征：

| 特征 | 表面优势 | 隐藏风险 |
|------|---------|---------|
| 快速生成 (10 分钟 diff) | 迭代速度快 | 理解时间被压缩 |
| 测试自动通过 | 质量有保障的假象 | 测试覆盖的是「代码正确」而非「需求正确」 |
|  verbose 输出 | 信息完整 | 关键决策被淹没在冗余解释中 |
| 上下文压缩 (200K tokens) | 长期记忆 | 10 分钟前的约定可能被遗忘 |
| MCP 工具集成质量参差 | 生态丰富 | 部分集成像「在信封背面写的 API 文档」 |

### 验证债务 vs 技术债务

| 维度 | 技术债务 | 验证债务 |
|------|---------|---------|
| **可见性** | 明显（构建变慢、依赖混乱） | 隐蔽（测试全绿、代码整洁） |
| **积累方式** | 主动选择「先上线再优化」 | 被动接受「看起来没问题」 |
| **爆发形式** | 渐进式摩擦 | 突然发现「构建错了东西」 |
| **修复成本** | 重构代码 | 重新理解需求 + 重构 |
| **心理机制** | 明知故犯 | 虚假信心 |

### 人类瓶颈转移

当 AI 让每个工程师生产力提升 50% 时，组织不会得到 50% 更多产出——而是得到 50% 更多的 PR、文档、设计提案。**瓶颈没有消失，只是向上游移动**：

```
传统瓶颈：写代码太慢
    ↓
AI 编码时代瓶颈：审查、决策、领域理解、风险判断
    ↓
不可自动化的部分：决定建什么、定义「完成」、理解业务、做权衡
```

## 实用评估

### 什么场景值得用

| 场景 | 理由 | 建议实践 |
|------|------|---------|
| 成熟 review 流程的团队 | 已有审查文化，可快速适配 AI 输出 | 在现有 checklist 中增加 AI 专项问题 |
| SQL/数据查询类任务 | 结果可快速验证，错误成本低 | 让 Agent 直接连接数据仓库探索（如文中 Snowflake 案例） |
| 原型验证/概念验证 | 快速试错，后续可重写 | 明确标注「AI 生成 - 待重构」 |
| 文档/注释生成 | 人类审查成本低，价值高 | 要求 Agent 基于实际代码生成，而非凭空编造 |

### 什么场景不值得用

| 场景 | 风险 | 替代方案 |
|------|------|---------|
| 缺乏代码审查文化 | 验证债务快速积累 | 先建立 review 流程再引入 AI |
| 领域知识不足 | 无法判断 Agent 假设是否正确 | 人类先学习领域，再让 Agent 辅助 |
| 高合规/安全要求 | 「看起来对」不等于「符合规范」 | 需要形式化验证或专门审计工具 |
| 核心业务逻辑 | 错误成本极高 | 人类主导，AI 仅做辅助建议 |

### 迁移成本

从「纯人工编码」迁移到「AI 辅助 + 系统化验证」：

| 阶段 | 工作内容 | 预计时间 |
|------|---------|---------|
| 意识建立 | 团队学习验证债务概念、识别风险点 | 1-2 周 |
| Checklist 设计 | 基于文中 4 个问题定制团队专属清单 | 1 周 |
| 流程嵌入 | 将 AI 验证步骤集成到现有 PR 流程 | 2-4 周 |
| 工具配置 | 配置 Agent 权限、设置审查触发条件 | 1 周 |
| 文化适应 | 团队习惯「审查 AI 输出」而非「自己写」 | 持续 2-3 月 |

**总成本**：约 1-2 个月完成初步转型，但文化适应是持续过程。

## 关键代码/配置片段

### 验证债务检查清单（源自原文）

```markdown
□ Agent 实现的是正确的逻辑，还是忠实地编码了一个有缺陷的规格？
  → 它不会质疑你的意图——除非你明确要求它质疑

□ Agent 对领域做了什么假设？
  → 这些假设在代码中可能不可见

□ 这个变更引入了什么权限、数据访问或副作用？
  → Agent 可能无意中扩大了访问范围

□ 你愿意为这个变更「签字背书」吗？
  → 它是否真的做了用户需要的——而不只是工单上写的？

如果最后一个问题的答案是「大概吧」，那你还没完成审查。
```

### AI 编码工作流的理想状态（文中描述）

```
当集成良好时：
  Agent 不再是「花哨的自动补全」
  → 而是真正的协作者：能调查、交叉引用、提出建议

当集成糟糕时：
  就像给实习生一张「一半街道是编造的」地图
  → 它会自信地走向不存在的地方
```
