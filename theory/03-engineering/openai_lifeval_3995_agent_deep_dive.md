- **與传统 agent benchmark 核心差異**：传统 benchmark（SWE-bench、GAIA、WebArena 一类）从「领域里有难度的事」出题，LifeVal 从「人口统计学意义上人们真正需要的事」出题，任务下限更日常、上限更模糊

## 是什么 / 解决什么问题

过去两年 agent 评测几乎都在往「更难」走：更长的工具链、更复杂的代码库、更刁钻的网页交互。但难度曲线和用户价值曲线并不是同一条。OpenAI 这次摆出的问题很直接：如果一个 agent 能修好大型仓库里的 bug，却没法帮一位刚搬家的家长把幼儿园报名理顺，那它对一周一亿多用户的 ChatGPT 来说算成功吗？

LifeVal 的做法是先把「人都把时间花在哪」搞清楚了。官方说明里给了两个数据源：美国劳工统计局的 American Time Use Survey 和国际的 Multinational Time Use Study。这两份长期调查提供了跨人口结构、跨时段、跨季节的日常任务目录。在此基础上 OpenAI 又补了一层：一份 3,995 人、人口统计学上有代表性的新调查，逐个任务问「你有多希望 AI 助手在这里帮你」。

这个组合很关键。时间使用调查告诉你**人做了什么**，3,995 人调查告诉你**人想被帮什么**——两者交集才是评测题。最终任务覆盖照护（caregiving）、健康、教育、家庭行政、个人财务、购物、政府服务办理等门类。这些都是「一个人必须亲自跑腿、打电话、填表、比价」的领域，也正是 agent 变现最直接的地方。

第二个问题是「怎么算做完」。LifeVal 的样例展示的都是有明确终态的流程任务，而不是问答。官方给出的几个例子和当前模型得分：

| 任务 | 模型达成率（官方 blog） |
|------|------------------------|
| 洪水前组织社区志愿者，为 4 户邻居做防洪准备 | 98.0% |
| 异地陪奶奶一起看球赛（含备用方案） | 96.3% |
| 搬家后比较幼儿园并给出报名清单 | 93.1% |
| 父母新诊断糖尿病后的第一周照护与饮食计划 | 90.4% |
| 在 Luzerne County 找符合预算、有独立居住单元、通勤合适的房子并加入契约购物车 | 100% |

注意最后一条 —— 100%。这个数字本身就是一个信号：当任务被允许由模型自己定义「完成条件」时，满分并不稀奇。这也是 LifeVal 最需要被追问的地方，后面会展开。

## 技术架构拆解

### 核心设计决策

- **任务来源从文献/专家改为人生时间数据**：用 ATUS + MTUS 做任务底稿，避免评测集只反映研究者的生活经验（典型偏差：全是编程、论文、数据分析任务）。代价是任务边界更模糊，评分更难自动化。
- **加一层「想被帮」的需求筛选**：3,995 人调查的作用是排序，不是罗列。这一步把「能做」和「值得做」区分开，是 LifeVal 方法论里最可复用的部分。
- **评测单位是「端到端流程」而非「单步正确性」**：从官方样例看，每个任务都有多步现实动作（收集信息 → 比较 → 决策 → 落到具体系统里执行，例如把契约加入购物车）。这比 trajectory 逐步骤打分更贴近用户体感，但也更难归因。
- **明确押注 agent 能力栈**：官方写明过去一年在 **browser use、computer use、connectors** 三类任务上做了训练，并把这套评测用于驱动模型改进。也就是说 LifeVal 不是事后观测，而是训练目标的一部分——这一点决定了它的分数不能当独立测量。
- **把「个人助理」定为 ChatGPT 的产品方向**：官方原话是把 ChatGPT 从 chat tool 推向 "a truly agentic personal assistant"。LifeVal 是这句话的度量尺。

### 与前版/竞品的关键差异

| 维度 | 传统 agent benchmark（GAIA / WebArena / SWE-bench 类） | LifeVal |
|------|------|------|
| 任务来源 | 研究者设计、领域难度驱动 | 时间使用调查 + 3,995 人代表样本需求 |
| 任务覆盖面 | 窄而深（代码、网页、检索） | 宽而日常（照护、健康、财务、政务、购物） |

| 可复现性 | 公开数据集，可第三方跑 | 未见公开任务集与 harness → TODO: 待确认是否开源 |
| 独立性 | 通常与具体厂商无关 | 单一厂商自建、自评、自用于训练 |

这张表里最关键的一行是「独立性」。LifeVal 的价值不在于给出一个可比的数字，而在于它把「用户价值」这个模糊词拆成了可执行的任务清单。

## 实用评估

### 什么场景值得用

- **设计 agent 产品时拿它当任务清单模板**：如果你的 agent 面向 C 端或家庭场景，「照护、健康、家庭行政、政务办理」这七个门类是很好的需求图谱。它比拍脑袋想的场景更贴近真实时间分配。
- **做 eval 时抄「需求分层」这一步**：先用人口数据定任务候选，再用代表性样本排序，这个流程几乎可以直接搬到企业内部（把 ATUS 换成工时记录/工单系统）。
- **判断产品形态趋势**：官方把方向压在 browser use + computer use + connectors 三件套上，这是个明确的信号——纯 API 集成型的 agent 能力栈不够，得能操作「没有 API 的世界」。
- **理解「完成」的定义变化**：从「回答正确」到「把事情落到某个真实系统里（购物车、报名表、日程）」，这个转变会影响你的工具设计。

### 什么场景不值得用

- **做模型横评**：没有第三方基线、没有公开任务集，把 93.1% 和别家的某个指标放在一起没有任何意义。
- **做采购或合规依据**：「我们自己评测自己」不构成审计材料。
- **推断真实世界的成功率**：样例任务都是被挑出来的，且允许模型自定义完成条件。100% 那一题就是典型——它说明的是任务可解，不是 agent 可靠。

### 迁移成本

如果你只是想借用方法论，成本很低：一到两周可以搭起内部版本（任务候选采集 → 需求排序 → 端到端任务定义 → 结果判定）。真正的成本在第三步之后的评分环节——生活任务的判定条件往往依赖外部状态（房子是否存在、报名是否成功），需要接真实系统或人工作业，这部分没有捷径。

## 对你的意义

Ken 这边的两个方向，这次的信号不太一样：

**AI App / Agent 方向**：值得立即吸收的是「需求分层」这一步。你们在做 agent builder 和 visual workflow，很容易陷入「能力 showcase」——能调多少工具、能跑多少步。LifeVal 提醒的是另一条轴：任务的终态是不是用户真正在乎的那个状态。做 workflow 产品时，「这件事做完的标志是什么」应该像节点类型一样被显式建模，而不是留给 prompt 去猜。

**VLA / 具身方向**：这里有一个跨领域的结构性对应关系，值得单独记一笔。LifeVal 做的是「用人的时间分配反推评测题」，VLA 领域长期靠的是「标准桌面抓取任务集」。具身智能同样缺一份「人在物理世界里真正需要机器人做什么」的需求侧目录——家务里占比最高的是整理、清洁、取放，而不是论文里主流的紧凑堆叠。谁先做出具身版的 ATUS，谁就掌握了下一轮任务定义权。这个类比不严谨，但方向我认为是对的。

**结论**：读方法，不要读分数。这篇文章真正的产出是那张需求门类清单和「browser use / computer use / connectors」的能力栈判断，而不是 93.1% 这个数。
