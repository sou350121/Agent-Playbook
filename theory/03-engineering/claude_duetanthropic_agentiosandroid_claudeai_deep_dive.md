## 是什么 / 解决什么问题

到 2026 年为止，绝大多数 Agent 产品的交互模型仍是被动的：用户输入 prompt，Agent 执行，返回结果。这带来一个隐性成本——**用户必须自己知道「该问什么」**，而专业人士一天要处理几十个决策，往往最难的部分不是执行，而是记住哪些事需要处理。

Claude Duet 换了一个方向：它每天早上发一份简短简报，汇总你已连接应用里最重要的条目；白天它持续盯着这些应用，**只在有事需要你时才发消息**。用户也可以直接把任务丢给它——从简单的安排会议，到构建包含几十个工具的仪表盘、创建财务或销售预测、做原型、写 Web App。

换句话说，它把 Agent 从「工具」变成「助理」。官方对它的定位相当克制：面向「盘子里的事超过自己能追踪范围」的专业人士与小企业主。

值得注意的是它的模型底座：官方说明 Duet **围绕 Claude Opus 5.5 设计**，并被塑造成「有判断力」的——决定什么需要你、什么可以等、什么时候要先问你。这是一个关键信号：主动式 Agent 的核心难点已经从「能不能做」转向「**知不知道该不该做**」。

## 技术架构拆解

### 核心设计决策

- **常驻虚拟机 + 自有浏览器**：Duet 不在你的笔记本或手机上跑，而在一个带独立浏览器的 VM 里。这意味着任务可以「人离开后继续」——关掉手机也照跑，完成后推通知。
- **上下文继承优先**：Duet 直接继承 Claude 账号里的 memory、skills 和已连接应用，几乎零配置就能开始。这是一个聪明的产品决策——把冷启动降到最低，避免「新 App 又要重新教一遍」的疲劳。
- **单一线程交互**：打字或语音都汇入同一条持续对话线程。官方明确选择这个设计：**一次快速回复和一个为期一周的项目从同一个地方开始**，不切分会话。
- **轮询而非持续监听**：Duet 每几个小时检查一次已连接账号，官方原文给出理由——「nonstop 检查会更快耗尽你套餐的限额」。这是一个诚实的工程-商业折中，也意味着它不是真正的实时监控。
- **人类保留关键决策**：读取、起草、准备可以自主完成；但**发消息、付款、签署文件、删除任何东西**之前，它会展示即将执行的动作并等待批准。
- **凭证隔离**：遵循 Claude Managed Agents 的凭证处理设计，Duet **从不直接看到你的密码或登录 token**。
- **动作审批复用 auto mode classifier**：与 Claude / Claude Code 使用同一套防护机制，防止做出你没要求的动作。
- **独立敏感信息分类器**：这是本次发布的新东西——一套专用分类模型 + 安全系统提示词，逐条检查消息，拦截最严格层级的信息（信用卡号、政府身份证明），健康 / 个人财务类信息只在用户明确指示发送时才放行。

## 实用评估

### 什么场景值得用

- **小企业主的后台运营**：官方列的示例相当具体——查 QuickBooks / Stripe 的未付发票并起草催款、在 Gusto 里准备并执行薪酬（含工时、奖金、报销）、起草招聘帖经你审核后发到 LinkedIn、通过 Docusign 准备协议并送签、用 HubSpot 的联系人历史起草跟进邮件。这些是典型的「知道该做但一直拖着」的任务。
- **需要跨应用的长链条任务**：构建仪表盘、财务或销售预测、原型、Web App。这类任务恰恰最怕「人得守着」，Duet 的 VM 架构在这里是真实的差异化。
- **高信息密度、低决策权的工作者**：每天被邮件/Slack 淹没，需要有人替他做第一层分流（什么漏了、什么要回）。
- **采购类支付**：通过 Stripe 的 Link 数字钱包，Duet 与你确认商品，Link 再让你批准支出，**用虚拟卡付款，真实卡号不外泄**。Shop Pay 也支持。

### 什么场景不值得用

- **非美国用户**：首发仅美国 Pro / Max，需排队。其他地区暂无时间表（待确认）。
- **需要实时监控的场景**：轮询周期是「几小时」，不是秒级或分钟级。做运维告警、行情监控会错过窗口。
- **需要审计执行过程的场景**：官方明确说**还无法展示它的浏览器**。合规审计要求的「可回溯操作链」目前拿不到。
- **纯生活助理**：官方自己也承认「围绕工作构建核心能力」，个人代办如订票「还不够强」。
- **金融交易类**：证券交易、账户间转账**即使你同意也不行**——这是硬性设计红线，不是配置项。
- **限额敏感的重度用户**：Duet **共享**你 Pro / Max 套餐的用量限额，且后台检查也计入限额，大任务（建财务模型、做 deck）需要更多模型轮次和后台工作。这意味着它会吃掉你主 App 的额度。
- **与主 Claude App 的无缝体验**：当前 Duet 是独立 App，与主 Claude App 分离，融合方式未定（官方：「早期用户的学习会塑造两者如何协作」）。

### 迁移成本

- **对终端用户**：几乎为零。上下文（memory / skills / 连接应用）从既有 Claude 账号继承，「设置需要最少的工作」。真正的成本是**认知迁移**——从「我要问什么」变成「我要批准什么」，以及接受一个会主动打扰你的存在。
- **对开发者/集成方**：如果已有 Claude 连接器或插件，Duet 直接复用 Marketplace 的 6,000+ 集成，无需重做。若要自建，成本主要在权限粒度设计与审批 UX——Duet 把「写操作前展示完整动作」做成了硬约束，你的集成必须在这个约束下设计。
- **时间估算**：官方未披露 connector 在 Duet 下的权限模型细节与适配工作量，待 preview 扩大后验证（此处为未知项，不作估算）。

## 对你的意义

几个观察点值得记下来：

1. **「判断力」正在成为产品化的护城河**。Duet 最核心的能力不是执行，而是「决定什么需要你、什么可以等」。这与 A-004（推理模型在 Agent 任务展现持续优势）方向一致——主动式 Agent 的调度决策本质是推理问题，Opus 5.5 承担的是优先级判断而非内容生成。
2. **安全层从「后置审查」变成「产品设计前置」**。Duet 在发布当天就同时推出专用敏感信息分类器、凭证隔离、审批闸门、红队 + 外部渗透测试、bug bounty。这不是合规补丁，而是首发的一部分。对做 Agent 产品的人来说，这是新基线——**主动式 Agent 没有安全层就无法上架**。
3. **架构上值得抄的只有两条**：① VM + 自有浏览器让任务「脱机持续」；② 读/写权限在架构层切分，写操作强制走审批闸门。其余（轮询周期、限额共享）都是待验证的商业折中。
4. **对你的项目建议**：**观望**。理由很实在——美国 Pro/Max 限额、research preview、无法观测浏览器、独立 App，这四项任何一项都足以让你在自己的工作流里踩坑。但这篇设计文档值得精读，尤其是「每几小时轮询以节省限额」这个成本-体验取舍，与你做 Agent 时的调度设计高度相关。
