## 技术架构拆解

### 核心设计决策

以下架构细节来自 Hy4-preview 的公开技术说明；正式版官方仅表述为「预训练与后训练规模显著扩大 + 首次引入视觉理解」，是否完整沿用同一套架构**待官方系统卡片确认**。

- **MoE 稀疏化控制推理成本**：主干 78 层，第 1 层为稠密 FFN，其余 77 层为 MoE；每层 256 个路由专家 + 1 个共享专家，每个 Token 只激活 8 个路由专家。总参数 770B，激活 49B。
- **百万 Token 上下文**：相比 Hy3 的 256K，窗口扩大约 4 倍。代价是注意力计算量暴涨，因此配套两项设计：
  - **Gated DSA 稀疏注意力**：为查询位置最多选择 2048 个相关 Token 再计算，而非全量关联。
  - **IndexCache 跨层索引复用**：部分层复用相邻层已算好的稀疏索引，减少重复筛选。
- **iHC（identity Hyper-Connections）**：把传统单条残差流扩展为 4 条，增加层间信息通路。
- **原生 MTP 推测解码**：主干外挂一层 MTP，10B 总参数 / 0.7B 激活，先草拟候选 Token 再由主模型验证。
- **专业软件专项训练**：针对 Blender、CAD 等软件与跨应用长程任务做了定向训练（正式版新增内容）。

一个必须讲清楚的取舍：**770B 总参数意味着权重必须完整存储和部署**，激活 49B 只降低单次前向的计算量，不降低显存占用。这不是「笔记本能跑」的模型。

## 实用评估

### 什么场景值得用

- **跨应用办公任务**：官方描述的可交付物是「文档、表格、演示文稿」，且强调跨文件协作。这类任务的瓶颈历来是「模型能不能看到最终排版效果」，视觉理解 + GUI 操作正好补上这一环。
- **专业软件脚本化**：Blender、CAD 的专项训练是少见的大厂投入。对做 3D / 工程自动化的人来说，这是目前开源模型里唯一点名覆盖的。
- **长程编码 Agent 的本地底座**：Terminal-Bench 2.1 从 70.8 → 85.4、DeepSWE 28.0 → 64.3 的跳幅说明它在「多轮执行 + 调试 + 验证」上的进步是真实且大幅的，且权重可私有化部署，数据不出内网。
- **超长上下文抽取**：1M 窗口下做代码库级理解或跨会议资料分析，比反复切块拼接的工程方案更省事。

### 什么场景不值得用

- **消费级硬件本地跑**：770B 权重需完整驻留，激活稀疏省的是算力不是显存。个人单机部署基本不现实。
- **低延迟在线对话**：腾讯自己承认该系列在复杂任务上「思考时间较长、过度自我验证」。把它塞进首字延迟敏感的聊天产品是错配。
- **需要第三方榜单背书才能采购的企业**：目前核心数字（85.4 / 64.3 / 内部盲测 2.99 vs GLM-5.3 的 2.92）**全部来自腾讯自建评测**，任务分布和环境由腾讯设计。在 LMArena、SWE-bench Verified 等第三方榜上出现独立复现之前，不宜当作「全面领先」的证据。
- **对视觉精度要求极致**：官方举的例子是细粒度图像处理、复杂图表分析、数学视觉推理，但没有给具体 benchmark 分数；这类能力的第一版通常需要实测验证。

### 迁移成本

- **从 Hy3 迁移**：架构同源、API 接入点不变（腾讯云 TokenHub / OpenRouter / Hermes / OpenCode 已同步接入），主要成本是显存预算重算——别指望沿用 Hy3 的部署配置。
- **从闭源 Computer Use 迁移**：动作空间与截图协议的抽象层需要重写，这是真正的工作量所在（参考 Anthropic 系的 tool schema 与各家 GUI agent 框架的差异）。约**待评估**，无公开迁移指南。
- **从 Hy4-preview 升级**：接口几乎无变化，主要新增视觉输入通道与 Computer Use 动作，需要重训 prompt 与工具描述。

## 对你的意义

如果手上在做 **Agent + UI** 方向的产品，Hy4 值得的不是「换模型」，而是**打开了一个可私有化部署的 GUI Agent 试验场**。此前做 computer-use 类产品，要么绑死闭源 API，要么用一堆小模型拼装，效果不稳定。现在有了一个 770B 级别、Apache 2.0 / 即将开源的选项，可以把「模型层」当成常量去调「交互层」。

3. **专业软件场景可以直接排期**：Blender / CAD 专项训练是差异化的，如果团队里有 3D 或工程自动化需求，这是最值得先试的一块。
