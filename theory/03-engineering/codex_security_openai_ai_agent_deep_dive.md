## 是什么 / 解决什么问题

现代软件开发面临一个核心矛盾：AI 加速了代码生成速度，但安全审查成为越来越关键的瓶颈。传统 AI 安全工具（如 SAST 扫描器）通常基于静态签名匹配，产生大量低影响发现和假阳性，迫使安全团队花费大量时间在分类（triage）而非真正修复漏洞。

Codex Security（前身为 Aardvark）是 OpenAI 推出的应用安全 Agent，旨在解决这两个挑战。它通过结合 frontier model 的代理推理能力和自动化验证，提供高置信度的漏洞发现和可操作的修复建议，让团队能够专注于真正重要的漏洞并更快发布安全代码。

该系统于 2025 年开始私人测试，早期内部部署中发现了真实的 SSRF 漏洞、关键的跨租户认证漏洞等问题，安全团队在数小时内完成修复。经过 beta 测试迭代，同一仓库的扫描结果显示精度持续提升，某案例中自首次部署以来噪声降低了 84%。

2026 年 3 月 13 日起，Codex Security 开始向 ChatGPT Pro、Enterprise、Business 和 Edu 客户推出研究预览版，首月免费使用。

## 技术架构拆解

### 核心设计决策

Codex Security 的设计围绕三个核心阶段，每个阶段都强调"上下文感知"而非通用签名匹配：

**1. 构建系统上下文与可编辑威胁模型**
- 扫描配置后，系统分析仓库以理解与安全相关的系统结构
- 生成项目特定的威胁模型，捕获系统功能、信任边界和最暴露点
- 威胁模型可手动编辑，保持与团队认知对齐
- 这是与传统工具的关键差异：传统 SAST 没有项目特定上下文

**2. 优先级排序与验证**
- 使用威胁模型作为上下文搜索漏洞
- 基于预期真实世界影响对发现进行分类
- 在沙箱验证环境中对发现进行压力测试，区分信号与噪声
- 当配置了项目定制环境时，可在运行系统上下文中直接验证问题
- 深度验证进一步降低假阳性，并支持创建可工作的概念验证（PoC）

**3. 基于完整系统上下文的修复**
- 提出与系统意图和周围行为一致的修复方案
- 修复方案在提高安全性的同时最小化回归风险
- 用户可筛选发现，聚焦对团队最重要、安全影响最高的问题
- 系统可从用户反馈中学习，调整发现的关键性评级， refine 威胁模型

## 实用评估

### 什么场景值得用

**中大型代码库的持续安全监控**
- 理由：beta 数据显示系统在 30 天内扫描了 120 万+ commits，识别 792 个关键发现和 10,561 个高严重性发现。关键问题出现在不到 0.1% 的扫描 commits 中，说明系统能在大量代码中识别安全影响问题同时最小化审查噪声。

**开源项目维护**
- 理由：OpenAI 已启动 Codex for OSS 计划，为开源维护者提供免费 ChatGPT Pro/Plus 账户、代码审查和 Codex Security。vLLM 等项目已将其纳入正常工作流程。维护者反馈痛点不是缺少漏洞报告，而是低质量报告过多 — Codex Security 优先高置信度问题。

**CI/CD 流程中的安全卡点**
- 理由：系统逐 commit 扫描，可在 PR 合并前发现并修复问题。修复建议与系统上下文对齐，降低回归风险，使审查和合并更安全。

**团队已有 ChatGPT Enterprise/Business 订阅**
- 理由：首月免费，后续无需额外采购独立安全工具，降低总拥有成本。

### 什么场景不值得用

**小型项目（<10k 行代码）**
- 理由：系统优势在于从大量代码中筛选高置信度发现，小项目人工审查成本本就较低，ROI 不明显。

**需要本地部署/数据不出境的场景**
- 理由：Codex Security 通过 Codex Web 云端运行，OpenAI 管理访问。不符合数据本地化要求的团队无法使用。

**预算有限的团队（无 ChatGPT 订阅）**
- 理由：需要 ChatGPT Enterprise/Business/Edu 订阅，独立采购成本未知但预计不低。

**需要即时全量扫描的场景**
- 理由：系统逐 commit 扫描，适合持续监控而非一次性全面审计。

## 关键代码/配置片段

Codex Security 通过 Codex Web 界面操作，无传统 CLI 配置。核心配置项包括：

**威胁模型配置（概念示例）**
```yaml
# 威胁模型结构（根据官方文档推断）
threat_model:
  system_description: "系统功能描述"
  trust_boundaries:
    - "用户输入边界"
    - "外部 API 边界"
    - "数据库边界"
  attack_surface:
    - "公开 API 端点"
    - "认证机制"
    - "文件上传处理"
  criticality_assumptions:
    - "用户数据泄露: 关键"
    - "服务中断：高"
    - "性能下降：中"
```

**扫描配置流程**
1. 在 Codex Web 中选择 Connected Repositories
2. 配置扫描范围（全仓库/特定分支）
3. 审查并编辑自动生成的威胁模型
4. 启动扫描，查看验证后的发现
5. 在 GitHub 中审查建议的修复 PR
