## 是什么 / 解决什么问题

AWS Generative AI Innovation Center（GenAI IC）在服务 1000+ 客户的过程中发现了一个普遍现象：企业在高管会议上问"我们在 AI 上投入够吗？"答案几乎总是"够"；但追问"哪些具体工作流因为 AI Agent 而实质性变好了？我们如何知道？"时，会议室会陷入沉默。

这中间的差距不是缺少基础模型或供应商，而是缺少**运营模型（Operating Model）**。

这篇文章的核心论点是：Agentic AI 不是一个可以打开的功能开关，而是对工作定义方式、执行者角色、决策机制的根本性转变。大多数企业在触及真实流程、系统和治理时，试点项目就会停滞——不是因为技术不行，因为没人对"成功长什么样"达成共识。

文章提出了一个关键视角转换：不要问"我们可以在哪里使用 Agent？"，而要问"哪里的工作已经结构化得像一个 Agent 可以做的职位？"

## 技术架构拆解

### 核心设计决策

AWS 团队基于实战经验提出了 Agent 就绪工作的**四要素框架**：

```
┌─────────────────────────────────────────────────────────────┐
│              Agent-Shaped Work 四要素                        │
├─────────────────────────────────────────────────────────────┤
│  1. 清晰的起点、终点、目的                                    │
│     - 任务触发条件明确（claim arrives / invoice appears）    │
│     - 目标可识别，完成状态可判断                              │
│     - 能处理合理的变化而无需显式指令                          │
├─────────────────────────────────────────────────────────────┤
│  2. 需要跨工具的判断力                                        │
│     - 不是固定脚本，需要推理选择信息源和工具                  │
│     - 系统必须有良好定义、安全、可靠的接口                    │
│     - 传统自动化 vs Agent：路径不是硬编码的                   │
├─────────────────────────────────────────────────────────────┤
│  3. 成功可观察、可度量                                        │
│     - 外人能判断输出是否正确而无需读心                        │
│     - 可追溯推理过程：用了什么数据、调了什么工具、为什么选 A 不选 B │
│     - 无法评估推理 = 无法改进 Agent = 无法为错误决策辩护      │
├─────────────────────────────────────────────────────────────┤
│  4. 出错时有安全模式                                          │
│     - 早期候选任务应该是可逆的或输出需人类确认                │
│     - 错误能快速发现、低成本纠正、不造成不可逆伤害            │
│     - 随着信任和控制成熟，再进入高利害闭环任务                │
└─────────────────────────────────────────────────────────────┘
```

### 迁移成本

从传统自动化或现有 AI 试点迁移到这套框架需要的工作：

| 迁移任务 | 工作量估计 | 关键挑战 |
|---------|-----------|---------|
| 工作流文档化（painful detail） | 2-4 周/工作流 | 需要一线员工参与，管理层容易低估细节复杂度 |
| 工具接口标准化 | 4-8 周 | 遗留系统可能没有 API，需要封装层 |
| 建立评估指标体系 | 2-3 周 | 需要定义什么是"可观察的成功" |
| 设计升级规则（escalation） | 1-2 周 | 需要明确 Agent 何时应该交还人类 |
| 建立定期回顾机制 | 1 周设置 + 持续 | 需要固定日程和负责人，容易流于形式 |

**总估计**：首个 Agent 工作流从评估到生产就绪约 2-3 个月，后续工作流可复用框架加速到 1-2 个月。
