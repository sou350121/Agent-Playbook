## 是什么 / 解决什么问题

Agent 有用但"通用"——它能做很多事，却不知道某个人、某个团队、某家公司**具体怎么做**这些事。Agent Skills 就是补上这块缺失上下文的东西：一段给 Agent 复用、针对某个具体工作的指令，简单到可以只是一个用自然语言写的文件。

Anthropic 于 2025 年 10 月提出 Agent Skills 概念，Vercel 在三个月后上线了 skills.sh 注册表。七个月内，这个注册表增长到 **100 万个 skills**、累计约 **2.8 亿次安装**。

这份报告的价值在于：它用同一套聚合数据同时观察了**供给侧**（作者发布了什么，即 published listings）和**需求侧**（用户装了什么，即 installs），从而揭示了一个反直觉的结构性事实——**供给高度技术化，需求高度分散化**。理解这个错位，对任何想构建或消费 Agent 能力的人都很关键。

## 技术架构拆解

### 核心设计决策

- **Skill 的极简定义**：一个 skill = 针对某项工作的可复用指令，可以用普通自然语言写。它不重复底层能力（Agent 和其工具已经提供），只补充"这一步怎么做、什么算做好、如何评估结果"这类**判断**。这使它比传统软件更快、更容易创建。
- **注册表 = 分发层**：skill 一旦写好，无需为每个 Agent 重写即可分发安装。这把它从"每个团队各自造轮子"变成了一个可复用的公共目录。
- **报告的数据方法**：目录总量按唯一 listing 计；安装量用聚合计数器（不代表独立用户或独立选择）；功能/行业结论基于**已分类样本**而非全量目录。这一点对解读数字很重要。

### 与前版/竞品的关键差异

报告把 skills.sh 的增速与其他平台做了直接对比：

| 平台 | 达到 100 万单元所需时间 |
|------|------------------------|
| skills.sh | 7 个月 |
| GitHub（repositories） | 27 个月 |
| App Store（apps） | 约 5 年出头 |
| npm（packages） | 超过 9 年 |

差异的根因在于"谁能创造"：能描述工作该怎么做的人，远多于能编程实现的人。skills 把更大的创作者池，接到了软件的复用能力上。

### 供需结构：供给技术化，需求分散化

| 维度 | 供给（listings） | 需求（installs） |
|------|-----------------|-----------------|
| 集中度 | 一半以上是软件工程 / Agent 工作流 / 数据 / 基础设施 / 安全，其中软件工程约占四分之一 | 没有单一类别超过五分之一的安装量 |

一句话概括这个错位：**写 skill 需要你懂一份工作，装 skill 只需你想把这件事做完**。技能多半是技术性的（因为它们诞生于开发者工具），但安装覆盖了公司里每一个职能。

## 实用评估

### 什么场景值得用

- **沉淀"公司专属判断"**：报告的核心论点是，公开技能 + 更强的模型会让通用专业能力变成所有人的**基线**，差异化价值将转移到公司特有判断上（"客户什么时候能退款""什么改动不需二次评审"）。这正是内部 skill 的最佳落点。
- **补齐 Agent 的通用能力**：Agent 工作流与自动化占已分类安装量的 14.8%，仅次于软件工程；在安装量 ≥10 万的 listing 中，Agent 工作流是**最大类别**。规划、路由、工具调用、浏览器自动化这类跨任务能力，一次安装可复用到几乎所有工作。
- **跨行业能力优先**：跨行业 skill 占已分类技能的 66%，却拿下 **87.5% 的安装量**，平均每个 listing 的安装量是行业专属 skill 的 **3.6 倍**。可移植性就是价值。

### 什么场景不值得用

- **靠公开 skill 建护城河**：数据高度集中——**近半数 skill 只被安装过一次**；375 个 skill（占注册表 0.04%）拿走 62% 的安装量，**前 1.2% 拿走 94%**。即便最受欢迎的 skill，也占不到总安装量的 1%。头部效应极端，尾部几乎无人问津。
- **把安装量当质量指标**：报告自己指出，随着模型变强，"一个 skill 只有在让 Agent 做得比没有它更好时才成立"，质量衡量将从**流行度**转向**有效性**（tests / benchmarks）。今天用安装量排序，未来参考价值会下降。
- **平台/生态依赖提示**：数据来自 skills.sh 单一注册表（Vercel 运营），安装计数器不代表独立用户，功能/行业结论基于已分类样本——引用这些比例时须带上这个前提。

### 迁移成本

报告性质决定它不存在"迁移"。真正的动作成本是**创建与维护**：把团队判断写成一个 skill 门槛很低（自然语言文件即可），但报告预判下一代 skill 会像代码一样被**维护**（写下来、测试、积累）。也就是说，采用者需要接受"skill 是要养的资产，不是一次性配置"这一心理模型。

## 对你的意义

如果你在做 Agent + UI / RAG / LLMOps 方向，这份报告给出了三条可操作结论：

1. **立刻值得做**：把团队里反复出现的判断（评审标准、发布门槛、路由策略）写成内部 skill——这是公开能力沦为基线后，唯一还会增值的部分。
2. **可观望**：不要急着在公开 skill 市场上做"广度生意"，头部集中度数据基本否决了这条路；除非你能瞄准某个高频、跨行业、且现阶段被低估的具体工作。
3. **要跟踪**：未来 1–2 个季度的关键信号是**"skill 有效性评测"**是否出现——一旦出现第三方 benchmark（类似 agent 的 SWE-bench），skill 生态会从"数量竞赛"转入"质量竞赛"，届时选型标准会整个改变。

跨领域提示：这与 VLA 领域的"技能库/primitive 库"思路同源——都是把可复用能力从模型权重里解耦出来，作为独立层管理。若 VLA 侧出现类似"skill registry"的标准化分发，两线可以互相印证。
