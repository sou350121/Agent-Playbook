## 是什么 / 解决什么问题

过去一年多，第三方 Agent（尤其是 OpenClaw 这类可在本地或云端运行的个人智能体）最自然的分发渠道之一就是「消息 App」——用户希望像发消息一样给自己的 Agent 下指令。但这条路径在 WhatsApp 上一直是灰色的：用户自行搭建非官方 bot 接入 WhatsApp，常常直接导致账号被封。Telegram 则反过来拥抱了这个趋势，成为当前用户与本地/云端 Agent 交互的主要平台之一。

WhatsApp 这次的动作，本质上是**把这个灰产式的接入方式官方化、产品化**：与其让用户冒着封号风险跑第三方 bot，不如由平台提供一个受控的、可管理的「Agent 接入」入口。据 WABetaInfo 观测，该功能随 WhatsApp beta for Android **2.26.35.3** 开始滚动推出，目前仅有少数国家/地区的少量用户可见，官方未公布全量时间表。

它解决的核心痛点有两个：一是**账号安全**（不再需要非官方接入）；二是**分发摩擦**（消费者不必再打开独立 App、网站或浏览器扩展，直接在 WhatsApp 内即可与 Agent 对话）。

## 技术架构拆解

### 核心设计决策

- **API key 绑定模式**：WhatsApp 在设置中生成一枚 API key，用户将其粘贴到「托管 Agent 的第三方服务」里完成连接。这相当于把「谁会话、连哪个后端」的解耦权交给用户，平台侧不暴露复杂的 OAuth 配置流程。用户可随时在同一界面重新生成 key 以重置连接。
- **一对一会话 + 强隔离**：Agent 只能读取「用户在该会话中分享的内容」，**无法访问其他会话、联系人、媒体**。当前也**不能加入群聊和社区**。这是把「最小权限」当成产品默认值——牺牲了上下文丰富度，换取隐私边界清晰。
- **Meta 服务代持会话**：Agent 会话由 Meta 的一项服务「代表 Agent 开发者」进行管理，因此**不被视为端到端加密**——Agent 开发者作为服务的一部分，理论上可访问这些消息。平台明确把「人对人」的消息/通话（仍是完整 E2E）与「人对 Agent」的会话区分开。
- **支持 Agent 与 Bot 二合一**：接口同时接受 AI Agent 和普通 bot，只要服务兼容生成的 key 即可接入，平台不对后端是否由 LLM 驱动做限定。
- **数量上限 5**：每账号最多绑定 5 个 Agent，暗示平台在早期阶段对「多 Agent 并行分发」保持克制，避免滥用与资源失控。

## 实用评估

### 什么场景值得用

- **面向消费者的服务型 Agent**：例如预约、客服、查询类场景。WhatsApp 的用户基数意味着「零安装」触达，用户不必学习新 App。
- **需要在聊天里做轻量自动化的个人用户**：想给自己的本地/云端 Agent 一个合规的移动端入口，替代此前的高风险非官方方案。
- **多 Agent 分工的尝鲜者**：5 个上限之下，可为不同用途绑定不同 Agent（例如日程、笔记、查询各一）。

### 什么场景不值得用

- **需要丰富上下文的 Agent**：会话隔离意味着 Agent 拿不到用户的其他对话、联系人与媒体，任何依赖「全局上下文」的设计在此平台上直接不可用。
- **依赖群聊/社区分发的 Agent**：当前明确不支持加入群聊与社区，团队型、社群型 Agent 场景被排除。
- **对加密/合规有硬要求的场景**：Agent 会话**非端到端加密**，且 Agent 开发者可访问消息；涉及敏感数据的行业需谨慎评估。
- **追求即时全量上线的团队**：目前仅少数用户、仅 Android beta，官方未公布全量时间表，把它当作主渠道为时过早。

### 迁移成本

从 Telegram Bot（或自建非官方 WhatsApp 接入）迁移到 WhatsApp 原生 Agent，主要工作量在于：

1. **后端适配**：把「如何在托管服务中粘贴 API key 并建立连接」的流程封装成用户可自助完成的配置步骤（不同平台字段不同，官方称"most services have a field"）。
2. **能力裁剪**：移除所有依赖多会话/群聊/联系人的功能，改为单会话内的自包含上下文。
3. **安全声明**：在界面上向用户明确「会话非 E2E、开发者可访问消息」，避免合规与信任落差。
4. **留存设计**：注意「移除即断开、历史保留、重连需新 key」的行为，需要设计重连提示。

总体工作量取决于现有 Agent 对上下文/群聊的依赖程度；对单聊型 Agent 而言迁移成本较低，对上下文型 Agent 则是**架构级改造**。
