## 技术架构拆解

### 核心设计决策

- **开源 + 双形态（桌面端 / 代码启动的网页）**：把执行环境留在用户侧，而不是纯云端托管。对「整理本地文件、跑脚本、看仓库」这类任务，本地执行是必需项而非可选项；代价是分发、升级和权限治理全部更麻烦。
- **插件作为第一等扩展机制**：官方把「添工具、改界面、接入不同工作流程」都交给插件层，意味着 Harness 自身刻意保持轻，能力沉淀在生态里。这也解释了为什么插件数量会成为它最重要的对外指标。
- **官方 API 为统计与生态锚点**：DAU 与 token 口径都限定在「使用官方 API 的用户」。这不是技术限制声明，但说明生态的经济闭环是绑在官方 API 上的——插件可以调用本地能力，平台的计量与商业侧仍归官方。
- **先补基础设施，再开市场**：官方明确的三件事是「提升插件 API 稳定性与兼容性 → 完善插件安全机制 → 建设官方插件市场」。顺序值得注意：**先稳接口和权限，再谈分发**——这是插件生态里最容易做反的顺序。
- **作者激励先行试探**：Token 激励、技术交流、作品推荐被列为支持计划内容，但当前仅处于「收集初步意向」阶段，参与规则与细节待正式启动，**不能理解为已开放领取补贴**。

## 实用评估

### 什么场景值得用

- **本地/桌面型 Agent 任务**：整理文件、分析数据、跑脚本、仓库操作。桌面端形态天然适配本地文件系统，这是纯云端 chat 界面难以覆盖的。
- **团队内部能力插件化**：把内部工具（数据查询、报告生成、论文阅读管线）封装成 Harness 插件，让非工程同事也能在自己机器上复用——3.5 万插件的存量说明这条路已被社区验证可走通。
- **内容/研究流水线**：官方展示的插件案例集中在「创作台（脚本 + 封面 + 分镜）」「文章转网页/图卡」「论文阅读 + 翻译 + 标注 + 笔记」。如果你的工作流刚好是这几类，有现成积木可以少造轮子。
- **想要「可观察 Agent 上下文」的调试场景**：来源提到有专门查看 Agent 上下文的插件——这类工具对调 prompt 和排查失控行为很有用。

### 什么场景不值得用

- **需要合规与审计的企业平台**：官方尚未公布插件安全审核流程、隔离机制或具体权限规则。在拿到这些细节前，把 Harness 插件层放进受监管的生产链路是不成熟的。
- **需要稳定性承诺的生产依赖**：插件 API 的稳定性与兼容性被列为「将要提升」，也就是说**现在还不是稳定的**。频繁破坏性变更对插件作者和下游用户都是实打实的成本。
- **不打算用官方 API 的团队**：生态指标、作者激励与计量都围绕官方 API；绕开它接入第三方模型，你基本处于官方叙事的边缘地带，插件兼容性风险自负。
- **把 token 数字当商业信号的人**：92 万亿/日是官方自报且口径不明（未拆分输入/输出/缓存），不能反推收入或算力。

## 对你的意义

对 Agent + UI 这条线，这条新闻的价值不在数字，而在**平台化的判据**：一个 Agent 工作台要变成平台，必须依次补齐「接口稳定 → 权限与隔离 → 分发与发现 → 作者回报」。DeepSeek 目前把顺序摆对了，但四件事全都还在路上。这恰好给你一个可追踪的观察清单：后续如果官方公布**市场上线日期**、**插件权限模型**、**API 版本化策略**三者中的任意两项，说明平台化真正启动；如果只有 token 激励落地而安全机制缺失，那更像是增长动作而非平台建设。

具体建议：**观望 + 小规模试用**。如果你手上有一个「内部工具 → 可复用界面」的需求（例如把某个数据查询或论文阅读流程做成按钮），现在用 Harness 插件形式做一次原型是划算的——成本低，且能提前摸清 API 的粗糙之处。但不要把它写进任何需要 SLA 的关键路径，也不要现在就为「市场首发」投入大量开发。
