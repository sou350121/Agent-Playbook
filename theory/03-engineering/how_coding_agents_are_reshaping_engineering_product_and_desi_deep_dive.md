## 是什么 / 解决什么问题

Harrison Chase 這篇文章不是技術發布，而是一份**組織變革宣言**。他觀察到編碼 Agent（Claude Code、Cursor、Copilot Workspace 等）的普及正在根本性改變軟件工程團隊的運作方式。

**核心痛點**：傳統 EPD（Engineering, Product, Design）協作流程是線性的：
```
產品想法 → PRD 文檔 → 設計 Mock → 工程實現 → 上線
```
這個流程存在的理由是「實現成本高」—— 寫代碼、畫 Mock 都需要大量時間，所以需要專職角色和文檔來協調。

**編碼 Agent 的衝擊**：當任何人都能快速生成可運行的原型時：
- PRD 不再是必需的前置步驟
- 原型本身成為討論焦點
- 瓶頸從「怎麼做出來」變成「什麼值得做」和「做得夠不夠好」

這篇文章的核心論點是：**編碼 Agent 不是工具升級，而是生產關係重構**。

## 实用评估

### 什么场景值得用

1. **初創團隊 (5-20 人)**：通才價值最大化，一人可覆蓋產品→原型→審查全流程，溝通開銷最小化
2. **大型團隊重構期**：當團隊抱怨「流程太慢」「文檔太多」時，這是轉向原型驅動的信號
3. **個人開發者/獨立創作者**：用 Agent 槓桿放大個人產出，但需刻意培養產品 sense 避免自嗨
4. **技術負責人/架構師**：從代碼審查轉向架構審查，從「怎麼寫」轉向「為什麼這樣設計」

### 什么场景不值得用

1. **高度合規領域 (醫療/金融/航空)**：審查流程不能因 Agent 而簡化，文檔審計仍是必需
2. **團隊產品 sense 參差不齊**：壞的原型氾濫會拖慢整體進度，需先統一產品認知
3. **Agent 使用能力斷層大**：部分成員拒絕使用 Agent 會造成新的協作瓶頸
4. **從 0 到 1 探索期**：當問題空間本身不清晰時，原型驅動可能導致局部最優

### 迁移成本

從傳統模式轉向原型驅動模式需要：

| 變更項 | 工作量 | 關鍵動作 |
|--------|--------|---------|
| 流程重設計 | 中 (2-4 週) | 定義原型審查標準、意圖文檔模板 |
| 角色重新定位 | 高 (1-3 月) | 成員自我評估：構建者 or 審查者？ |
| 工具鏈適配 | 低 (1 週) | 統一 Agent 工具、建立共享組件庫 |
| 文化轉變 | 高 (持續) | 接受「更多原型、更快失敗」、建立心理安全 |

## 关键代码/配置片段

Harrison 在文章中提到一個有趣的觀點：

> "What if PRDs of the future are just structured, versioned prompts?"

這暗示未來的「需求文檔」可能是：

```yaml
# 範例：版本化的 Prompt 作為 PRD
version: 1.2
feature: user-authentication-flow
intent: |
  用戶應該能夠通過 Email 或 Google OAuth 登錄
  登錄後跳轉到 dashboard
  失敗時顯示清晰的錯誤信息
  
constraints:
  - 必須支持 rate limiting
  - 必須記錄審計日誌
  - 與現有 user 表兼容
  
test_cases:
  - 成功登錄 → 200 + redirect
  - 密碼錯誤 → 401 + 錯誤信息
  - 速率限制 → 429 + 重試提示
```

這種格式的好處：
- 可執行（直接餵給 Agent）
- 可版本控制（Git 管理變更）
- 可測試（test_cases 明確）
