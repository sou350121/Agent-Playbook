## 是什么 / 解决什么问题

Google Research 在 2026-10-29 的官方 blog 里提出了 **sleep framework**。它的出发点是一个所有做 agent 的人都熟悉的痛点：现代 LLM 靠预训练 + in-context learning 获得能力，但**一旦部署就基本是静态的**——知识截止日期固定，既不能吸收长期新知识，也不能适配新信息。

两条传统解法都不好用：

- **持续更新参数**：会触发灾难性遗忘（catastrophic forgetting），学新任务的同时严重破坏旧任务表现
- **纯靠 ICL**：知识留存被硬约束在 context window 内，session 一结束，短期信息就丢了

Sleep 框架的答案是把两者缝合起来：让模型拥有一个**连续的周期性生命周期**，在「醒着」与「睡着」之间交替，睡眠阶段专门做记忆巩固与自我提升。作者的定位很明确——不是让 context 更长，而是**让 context 里的东西在不用时变成参数**。

值得注意的是作者主动做的祛魅：blog 里明说"sleep""dreaming""self-improvement" 只是借用神经科学词汇，**整套机制完全运行在固定架构 + 人工设定的训练规则内**，模型不会自己长出新的代码或结构。

## 技术架构拆解

### 核心设计决策

- **双相位生命周期**：wake 相位按常规推理接收输入、把临时信息写进「高频短时记忆」；sleep 相位停止接收新输入，把算力转向巩固与自我改进。这是把训练/推理的严格二分改成可循环的后训练节奏。
- **参数扩容而非覆盖**：睡眠时模型**解锁预分配的 MoE 记忆块**，把新专家以低秩方式并入「稳定、低频的记忆块」。这是避免灾难性遗忘的物理前提——新知识有地方放，不用挤掉旧参数。
- **知识播种（向上的蒸馏）**：用 GKD（Generalized Knowledge Distillation）+ 基于 RL 的模仿学习，把高频层（如 in-context memory）里的脆弱记忆迁到新扩容的长期参数里。其中 on-policy distillation 让扩容后的 student 从自采样序列上的 teacher 分布获得 token 级反馈；LTI（Learning to Imitate）则用语义相似度 + Levenshtein 距离作为奖励。
- **突触修剪**：巩固完成后，**重置高频临时参数**，把容量还给下一轮 wake 相位。这一点很关键——它是「有限容量 + 无限期运行」能自洽的条件。
- **Dreaming 阶段**：REM 睡眠的类比。MoE router 在合成数据生成时**随机激活非标准专家**，强迫模型混合不同领域；生成「梦境」样本后用**基于梯度的数据筛选**挑出最有提升潜力的样本；最后对 top 样本做 SFT，并在下游任务上评估是否真的变强。

### 理论支撑

作者给了两段理论解释，而不是只堆实验：

- **巩固 = 结构化低秩压缩**：不是逐字复制短期轨迹，而是找出「既保住在策略行为、又保住语义奖励」的一组紧凑方向。on-policy distillation 让巩固对齐模型真实推理分布，语义奖励则改变「什么值得留」的判断标准。
- **Dreaming = 改善学习几何**：注入不同 MoE 拓宽梯度方向集合，梯度筛选强调信息量最大的合成经验，使优化景观更均衡、条件数更好——所以 dreaming 本质上是「有选择地多样化更新方向」，不只是数据增强。

## 实用评估

### 什么场景值得用

- **跨会话持续学习的 agent**：客服、研究助理、内部知识 agent——目前只能靠 RAG 反复检索，Sleep 提供了「真的记住」的路径。
- **超长文档 / 流式知识的离线压缩**：BABILong 上声称扩展到 10M tokens 近完美，这对需要处理长档案的管线有直接想象力。
- **低资源语言的持续翻译**：多阶段评估中在满语、Kalamang 等未见语言上近乎零性能下降，而 ICL、Cartridges、SFT 都出现严重遗忘——这是框架最干净的证据点。

### 什么场景不值得用

- **单次任务 / 无状态调用**：在没有跨会话累积需求时，睡眠机制纯属额外成本。
- **端侧 / 算力受限部署**：睡眠阶段涉及 MoE 扩容、蒸馏、合成数据生成与筛选，明显是数据中心级开销。
- **权重不可改写的合规场景**：模型行为会被自我改写，审计与可复现性会成问题；作者也未讨论安全护栏。
- **需要确定性输出**的场景：参数持续变化意味着同输入不同时间可能不同结果。

### 迁移成本

- **目前不存在"迁移"**：没有开源实现、没有 API、没有 checkpoint。短期内唯一可做的是**对照自己的 RAG pipeline 评估**：如果你的 agent 主要瓶颈是「检索召回不准 / 上下文塞不下」，Sleep 的方向值得跟踪；如果瓶颈是工具调用可靠性或编排，那它与你无关。
- 若要复现，论文（arXiv 2606.03979）是唯一入口，依赖 MoE 架构与 GKD 训练栈——以当前团队的 VLA 后训练经验看，这不是一周能验证的量级。
