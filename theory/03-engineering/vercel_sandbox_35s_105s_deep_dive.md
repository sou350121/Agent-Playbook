- **一句話定位**：Vercel Sandbox 新增**区域镜像缓存（regional image cache）**，镜像命中缓存时不再往返 iad1 的原始镜像存储，初始化快至原来的 4 倍。
- **現在值得用嗎**：是——只要你的 Sandbox 跑在 iad1 以外区域，而且用的是 Vercel 托管镜像或自建镜像（含基于它们打的快照）。

- **不適合場景**：只在 iad1 区域使用（改善本来就小）；镜像每次都要重建、缓存永远不命中的流水线。
- **與前版核心差異**：之前所有区域的镜像拉取都要回源 iad1；现在命中区域缓存就地读取，巴黎地区启动时间下降约 75%，首尔从 ~3.5s 降到 1.05s（官方内部端到端基准）。

## 是什么 / 解决什么问题

Vercel Sandbox 是 Vercel 提供的隔离执行环境（基于 Firecracker microVM），常被用来跑 AI 生成代码、执行不受信任的脚本、给代码 Agent 提供一个可随时销毁又能随时拉起的工作台。它的一个隐藏成本是**初始化阶段读取镜像数据**：镜像和快照都存在 iad1 的原始存储里，其他区域的沙箱启动时得跨区域往返拉取。

在 Agent 场景下这个成本被放大了：一次对话可能触发十几次沙箱创建，每次几百毫秒到几秒的启动开销会累积成肉眼可见的等待。Vercel 这次改动的核心就是**把镜像数据下沉到离沙箱最近的区域**——一旦区域缓存命中，初始化不再回源。

这次更新不是功能层面的新增，而是**执行层延迟结构的调整**：它不给你新 API，但改变了「多快能开始干活」这个基础常数。

## 技术架构拆解

### 核心设计决策
- **缓存位置前移，而非压缩镜像**：官方没有选择「把镜像做小」或「并行拉取」，而是把缓存节点放到各区域，命中即绕开跨区 RTT。线路距离问题用距离解决。
- **覆盖托管镜像 + 自建镜像 + 快照**：区域缓存支持 Vercel Container Registry 托管的 managed images 与 custom images，以及基于这些镜像创建的快照。意味着预装依赖、预热过的快照同样吃到加速。
- **对近源区域不做强行优化**：官方明确说明，离原始存储更近的区域提升幅度更小——这是物理距离决定的，不是实现缺陷。

## 实用评估

### 什么场景值得用
- **代码 Agent 执行层**：每轮任务都新建沙箱的架构收益最直接——启动时间从「几秒级」降到「一秒级」，交互体验变化明显。
- **非美国区团队 / 面向亚洲用户的产品**：首尔这类远程区域正是这次优化最显著的受益方。
- **基于快照的预热流程**：把依赖预装进镜像再打快照，缓存命中率高，加速稳定。

### 什么场景不值得用
- **纯 iad1 部署**：收益本来就有限，不值得为此调整架构。
- **镜像频繁重建的流水线**：每次新构建都意味着缓存未命中，加速失效，反而多了一层缓存管理心智负担。
- **超过 Sandbox 能力边界的需求**：需要长驻状态、持久化数据库、GPU 训练的场景，Sandbox 本身不是合适载体，启动快慢无关紧要。

### 迁移成本
- **代码改动**：零。这是平台侧行为变化，不是 API breaking change。
- **真正的工作量在验证**：需要在目标区域实测你自己的镜像（尤其是 custom image）命中率与启动时间，因为官方数据基于 Managed Images。
- **注意点**：首次在区域创建沙箱必然是冷缓存，流量分布不均的长尾区域收益需实测。
