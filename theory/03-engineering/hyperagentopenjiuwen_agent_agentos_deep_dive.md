## 是什么 / 解决什么问题

过去两年的 Agent 工程实践，基本围绕一个循环展开：模型思考 → 调用工具 → 观察结果 → 再思考。LangGraph、CrewAI、AutoGen 这些框架把「一次执行」的编排做到了相当成熟。但当你真的要把一个 Agent 放进生产、让它连续在线数周，问题就换了一批：

- 会话结束，状态就碎了；
- 工具或环境变了，Agent 不会自己适配；
- 多个 Agent 协同时，谁来分配算力和模型；
- Agent 自己改自己的代码（RSI，递归自我改进）时，确定性怎么保证。

openJiuwen 的 HyperAgent 主张正是冲着这批问题去的。它给出的核心判断是：**Agent 兼具「软件程序」与「智能主体」双重属性**——前者要求可部署、可观测、可扩展、成本可控；后者要求主动、永续、成长、协作。

据此它提出八项核心特征，可以清晰地对半切开：

| 属性 | 核心特征 | 对应的工程关切 |
|------|----------|----------------|
| 智能主体 | 主动性 | Agent 能否自发起任务，而非只响应请求 |
| 智能主体 | 永续性 | Agent 是否有跨会话的持续存在 |
| 智能主体 | 成长性 | Agent 能否从经验中改进自身 |
| 智能主体 | 协作性 | 多 Agent 之间如何分工与协同 |
| 软件程序 | 确定性 | 行为是否可复现、可审计 |
| 软件程序 | 扩展性 | 新工具/新能力如何接入 |
| 软件程序 | 开放性 | 是否绑定单一模型或平台 |
| 软件程序 | 经济性 | 算力与模型调用成本是否可控 |

## 技术架构拆解

### 核心设计决策

- **双属性切分，而不是单一「智能体」叙事**：把 Agent 当软件看，就必须有运行时、有可靠性、有成本模型；当智能主体看，才谈得上主动性。这个切分是整份架构的地基。
- **按「主体能力」与「应用能力」两条线组织 AgentOS**：主体侧围绕永续、协作、演进，应用侧围绕运行时、扩展、操控、成本。两条线互不干扰，各自可以独立演进。
- **事件驱动全双工交互**：Agent 不等用户开口，而是订阅事件流——这是「主动性」在协议层的落地方式，也直接决定了系统从 request-response 转向 event-driven。
- **Persistent Agent 作为一等公民**：Agent 实例跨会话存活，状态与记忆由平台承载，而不是塞进 prompt。
- **CoRSI（协同递归自我演进）**：把 RSI 从单 Agent 的自改代码，升级为多 Agent 协同的集体演进，用协作来对冲单点自我修改的风险。
- **异构蜂群协作**：允许多种不同模型/框架的 Agent 编组，而不是强制统一技术栈。
- **算力与模型路由协同的成本优化**：把「用哪个模型」当作运行时调度问题处理，而非写死在代码里。

### 底层机制分析

这套架构最值得拆的是「永续性」与「确定性」这对张力。Persistent Agent 想要长期存在、持续学习，天然与可复现、可审计冲突。openJiuwen 的解法看起来是把二者分层：记忆与状态归 Persistent Agent，行为边界与执行约束归分布式可靠运行时。换句话说，Agent 可以「记得更多、变得更好」，但每一次执行仍然落在受控运行时里。

第二个值得拆的是 CoRSI。「递归自我演进」在单体 Agent 上一直是高风险动作——改坏了自己就没了。把它变成多 Agent 协同演进，等于引入了一组互相校验的同行，这是把 RSI 从「单点赌注」变成「群体博弈」的思路。

## 实用评估

### 什么场景值得用

- **长期在线的个人助理类产品**：会话碎片化是这类产品最大的体验断点，Persistent Agent 直接面对这个问题。
- **企业多 Agent 分布式部署**：当 Agent 数量上升到几十个、由不同团队用不同框架开发时，异构蜂群与统一运行时才有意义。
- **研究型系统（RSI 方向）**：如果团队本身在探索 Agent 自我改进，CoRSI 提供了一个「协同而非单体」的参照设计。

### 什么场景不值得用

- **单轮问答或纯 RAG 检索**：八项特征里至少四项（主动性、永续性、成长性、协作性）用不上，引入 AgentOS 只会增加运维负担。
- **强合规、强审计场景**：Agent 具有主动发起行为的能力，意味着行为面扩大，审计与权限模型需要重新设计，成本可能超过收益。
- **团队规模小于 3 人的早期项目**：分层 AgentOS 的价值随 Agent 数量增长而上升，早期项目自建一层薄封装更划算。
- **模型能力敏感的竞赛型任务**：这套架构关注系统层，不解决模型本身的推理上限。

### 迁移成本

- 从 LangGraph / CrewAI 迁移：核心工作量在「状态外置」和「交互模型改造」——同步调用改成事件订阅，会话状态从内存搬到持久层。粗估中等偏重，取决于现有 Agent 的状态耦合程度。
- 从自研框架迁移：主要成本是接受新的运行时约束与部署形态。
- 生态成熟度是最大不确定项，应先评估开源实现的文档完备度和社区活跃度再做决定。

## 对你的意义

Ken 这条线做的是 Agent + UI。HyperAgent 这份八项清单，最直接的用途不是「换框架」，而是当作**架构评审 checklist**：

1. 你现在的 Agent 系统，八项特征里有几项其实是缺的？多数项目在「确定性」和「经济性」上有答案，在「永续性」和「成长性」上几乎是空白。
2. 「事件驱动全双工」这个交互模型，对 Agent UI 有直接启发——UI 从「用户敲一下、Agent 回一句」变成「Agent 订阅事件、主动推送状态」，这是一个产品形态层面的分叉。
3. 「算力与模型路由协同」和你已经在做的双模型策略是同构思路，可以互相印证。

具体建议：**观望但记下清单**。短期不必迁移技术栈，但把八项特征抄进设计文档，下次做 Agent 架构评审时逐条对照，投入产出比极高。如果 WorkSwarm 的开源实现成熟度足够，值得找一个内部项目做小范围验证。
