## 是什么 / 解决什么问题

Claude 现有的「经典记忆」模式本质上是一张不断滚动的便签纸——它把了解到的用户信息压缩进一条单一摘要里。问题显而易见：信息量一大，摘要就开始溢出，旧的被新的覆盖，重要的被琐碎的淹没。Claude 记住了你昨天点的咖啡口味，却可能忘了你上个月花三个小时讨论的产品架构。

Anthropic 的解决方案是一次彻底的范式转换：给 Claude 造一个内置的「个人 Wiki」。Memory Files 让 Claude 在对话过程中根据话题、项目或上下文自动编写并组织结构化文档；Dreams 在会话间隙异步运行，像人类 REM 睡眠一样整合、去重、更新记忆；Conway 则提供了 7x24 小时永不下线的运行时，让 Claude 从被动应答变为主动执行。

这三块拼图合在一起，构成了一条从记忆存储 → 记忆维护 → 记忆应用的完整链条。

## 实用评估

### 什么场景值得用

- **长期项目协作**：如果你和 Claude 协作一个持续数周甚至数月的开发项目，Memory Files 能让 Claude 记住每个模块的设计决策、技术选型、已知问题，不需要每次重新 briefing
- **多主题知识管理**：同时追踪多个领域（如 VLA 研究 + AI 应用开发），Memory Files 可按话题分离记忆，避免上下文污染
- **7x24 监控与执行**：Conway 适合需要持续运行的任务——代码仓库监控、CI/CD 触发、定期数据抓取、异常告警等
- **企业级 Agent 部署**：相比 OpenClaw（头两个月发现 9 个 CVE、4.2 万暴露实例），Conway 跑在 Anthropic 托管云上，安全底线更高

### 什么场景不值得用

- **一次性问答**：如果只是偶尔问个问题，经典记忆足够，Memory Files 的额外复杂度没有价值
- **对数据隐私极度敏感**：Conway 常驻后台意味着你的数据和任务持续运行在 Anthropic 云端，不适合处理敏感商业数据
- **需要本地部署的场景**：目前 Conway 完全基于 Anthropic 托管云，不支持本地化部署
- **预算敏感**：Conway 的 7x24 运行必然带来更高的计算成本，需要评估 ROI

### 迁移成本

| 迁移路径 | 工作量 | 说明 |
|----------|--------|------|
| 经典记忆 → Memory Files | 低 | 一键切换，经典记忆内容会自动迁移 |
| 第三方 Agent（OpenClaw/Hermes）→ Conway | 中 | 需要重新配置 Agent 逻辑，但 CNW ZIP 扩展格式提供了迁移路径 |
| OpenAI/Gemini 记忆 → Claude 记忆 | 中 | 需要手动导出/导入记忆内容，格式不兼容 |
