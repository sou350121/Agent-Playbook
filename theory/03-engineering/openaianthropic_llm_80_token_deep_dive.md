### 关键推算：缓存降价为何等于 70%+ 总成本下降

作者的推理链很干净，值得直接抄进自己的成本模型：

1. agent coding 场景中，cache read 占总支出 **96%–99%**；
2. 缓存命中率约 **90%–100%**；
3. 因此 cache read 单价降 **75%** → 总成本降 **70%–75%**。

反过来也成立：一个 output 单价砍半、但缓存单价没动的模型，对长会话 agent 的账单影响可能只有个位数百分比。这正是「GPT-6 Astra 与 Fable 5.1 同价但无低缓存价」被单独点出的原因——两者表面同价，实际每轮成本差一个量级。

一个重要推论：**上下文体积是被低估的杠杆**。同一模型下，把系统提示从 8k 压到 3k、或减少工具返回的冗余日志，对账单的影响可能大于在 GPT-6 Sol 与 Opus 5.5 之间来回选。

## 实用评估

### 什么场景值得用

- **长会话 coding agent 的成本建模**：按「cache read 单价 × 平均上下文长度 × 轮数」估月成本，比按 token 总量估更接近实际账单。
- **多模型路由的定价依据**：把主模型（负责规划、大 diff）放在低缓存价的高档模型，把清理型任务（格式化、日志摘要）放小模型；两者在缓存价上的差异会放大到路由决策里。
- **和财务/上级对齐口径**：当有人说「换便宜模型了怎么没省」，可以用 96%–99% 这个结构性事实解释——被换掉的往往不是成本主导项。
- **供应商选型评审**：把「cache read 单价」和「缓存 TTL / 命中率保证」列入评估表格，这是多数 RFP 模板里缺的两行。

### 什么场景不值得用

- **单轮或无状态调用**：没有缓存复用，三段式中只有 input/output 两段有意义，本文的核心洞察直接失效。
- **短上下文任务**（分类、抽取、短问答）：cache read 占比不会到 96% 量级，单位经济学结论不可移植。
- **需要精确 benchmark 依据的采购决策**：本文的模型表现评价（如「GPT-6 Sol 表现不佳」「Opus 5.5 优于 Fable 5.1」）来自作者观察与社区反馈，属于**据用户反馈**级别，不可作为唯一依据。
- **把本文当成价格权威源**：所有价格都是转述。厂商 pricing 页才是唯一权威，且这类价格变动频率以周计。

### 迁移成本

几乎为零——这是一篇分析文章的框架，不是需要安装的东西。实际要做的是两件事：

1. 在现有 agent 的日志里补两个字段：**cache read tokens / cache write tokens** 与 **每轮上下文 token 数**；
2. 把成本报表从「月 token 总量」改成「月 cache read 支出 + 月非缓存支出」。
