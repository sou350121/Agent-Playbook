## 技术架构拆解

### 核心设计决策

**决策 1：导师策略（Advisor Strategy）——执行与指导分离**

在 Messages API 中通过 tools array 配置双层架构：执行层用小模型（Haiku/Sonnet），指导层用大模型（Opus）。当执行层卡壳时，自动向导师模型"请教"。

效果：Sonnet + Opus 导师的总成本比单独跑 Sonnet 更低，因为 Opus 的一语道破让 Sonnet 少走了弯路。Eve Legal 用此策略以 1/5 成本达到前沿模型级别质量。

**决策 2：多智能体独立上下文窗口**

指挥官智能体协调多个子智能体，每个子智能体在独立线程中运行、拥有独立上下文窗口。让它们独立思考后汇总结果，效果优于共享上下文。

**决策 3：目标导向（Outcomes）作为独立验证层**

用户用 Markdown 定义验收标准，系统自动切出"阅卷智能体（Grader agent）"在会话过程中持续评估。可设定最大迭代次数，未达标则自动重试。

**决策 4：模型造梦（Dreaming）——自主学习闭环**

智能体在空闲时回顾历史会话，反思遗漏的技能和教训，自动写入记忆库。这不是 RAG，而是模型主动总结经验并结构化沉淀。

## 实用评估

### 什么场景值得用

- **复杂工程任务的多 Agent 协作**：如演示中的月球无人机着陆场景——需要指挥官统筹、探测员寻矿、领航员驾驶三个独立智能体协作。每个智能体有独立上下文，避免信息过载。适合需要多专业领域知识融合的工程场景。
- **需要自主迭代的智能体系统**：Outcomes 让你用 Markdown 定义验收标准，Grader agent 自动评估并触发重试。适合有明确质量门槛的自动化流程（如代码生成后的测试验证、文档生成的格式检查）。
- **CI/CD 自动化**：Auto-fix 监听 CI 失败、代码冲突、安全漏洞，自动修复并提补丁。Anthropic 内部工程师 PR 数量暴增 200% 的关键基础设施。适合任何有 CI/CD pipeline 的团队。
- **异步开发工作流**：Routines 让你配置一次触发规则（Webhook/定时/API），Claude 自动执行。Boris Cherny 表示他大部分代码现在是 Routines 写的——他创建的是"给 Claude 下发提示词的 Routine"。适合希望"早上醒来有一堆待合并 PR"的开发者。
- **成本敏感的大规模部署**：导师策略（Sonnet 执行 + Opus 指导）在保持前沿质量的同时降低 80% 成本。适合免费增值模式、高并发场景。

### 什么场景不值得用

- **简单代码补全**：如果你的需求只是编辑器内的代码补全和简单重构，传统的 GitHub Copilot 或 Cursor 更轻量、更便宜。Claude Code 的重型架构是杀鸡用牛刀。
- **严格数据主权要求的场景**：托管智能体的数据经过 Anthropic 基础设施处理。虽然数据归用户所有且可导出，但对于金融、医疗等需要数据完全本地化的场景，需评估合规风险。
- **预算极度受限的初创团队**：虽然导师策略降低了成本，但 Opus API 的绝对成本仍然不低。如果预算紧张，Haiku 级别的模型可能无法满足复杂任务需求。
- **对延迟敏感的场景**：多智能体编排 + Outcomes 迭代 + Dreaming 自主学习都增加了端到端延迟。如果需求是实时响应（如聊天机器人），这套架构过于重型。

### 迁移成本

- **从 Cursor/Windsurf 迁移到 Claude Code**：中等。CLI 和 IDE 插件的使用方式类似，但 Routines 和 Auto-fix 是全新概念，需要重新设计 CI/CD 流程。内部迁移：Anthropic 工程团队规模急剧扩张的同时 PR 数量暴增 200%，说明迁移曲线相对平缓。
- **从开源 multi-agent 框架迁移到 Claude Platform**：中高。需要重写智能体配置（从 Python/JSON 转为 Claude API 调用），但获得的是托管基础设施、内置记忆、自动验证——省去了大量自研运维成本。Notion 选择托管智能体的理由是"既要速度又要规模"。
- **引入导师策略**：低。只需在 Messages API 中更新 tools array，无需改动业务逻辑。
