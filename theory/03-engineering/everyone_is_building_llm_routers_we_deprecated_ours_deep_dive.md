## 是什么 / 解决什么问题

LLM Router（模型路由器）是近两年 AI 基础设施领域最热的概念之一。其核心逻辑看似简单：不是所有请求都需要 GPT-5 或 Claude 4 这样昂贵的模型——简单问题用便宜模型，复杂问题用强模型，从而降低推理成本。

Manifest 在 2026 年 3 月推出了自己的 LLM 路由器功能，作为其 LLM Gateway 的核心特性。路由器将每个请求分为四个复杂度层级：simple、standard、complex、reasoning，然后路由到对应档次的模型。

但在 4 个月的实际运营中（7000 云用户），Manifest 团队发现了路由策略的根本性缺陷。2026 年 6 月宣布弃用，9 月 1 日正式下线。这篇文章是他们用真金白银换来的工程反思。

## 技术架构拆解

### 核心设计决策

Manifest 的弃用决定基于四个维度的实践观察：

**1. 提示词无法独立决定任务复杂度**

这是路由器的致命弱点。提示词只是触发器，真正的复杂度在后续的工具调用、web 搜索、代码仓库分析等环节才逐步展开。

举例：`"evaluate the tests for the repo $GIT_REPO and improve them"` — 如果目标是个人静态网站，这是 simple 级别；如果目标是 Linux 内核仓库，这是 reasoning 级别。路由器在收到提示词的瞬间无法区分这两者。

**2. 缓存比路由更能降本**

缓存读取比未缓存输入便宜 75%-90%。系统提示词和对话历史通常占大量 token，且位于提示词前缀 —— Prefix Cache 对此效果极佳。

一个"感知缓存的路由器"会怎么做？它会增加对初始选中模型的"粘性"（stickiness），持续查询同一模型以利用缓存。讽刺的是，路由器最好的工作方式就是"不工作"——不做路由。

**3. 模型切换破坏行为一致性**

Manifest 强烈反对"工程师不应该关心选哪个模型"的观点。他们的立场是：

> "就像画家知道该用哪支画笔，工匠精心选择工具，工程师应该理解不同模型的 trade-off 和微妙差异。"

在 Manifest 的设计哲学中，每个工程师都基于自己的意图选择模型和参数。在工作会议中频繁切换模型会导致整体工作质量下降，并让团队与工具脱节。

**4. 不可预测性本身有成本**

在自动化 agentic 工作流或自主 agent 中，额外增加一层不确定性，其管理成本可能超过节省的推理费用：

- Evals（评估）变得更难：同一输入可能产生不同输出
- System prompts 需要为每个模型单独调优
- 可观测性系统需要处理多模型行为差异
- 调试和复现问题变得复杂

## 实用评估

### 什么场景值得用（路由方案）

- **独立批处理任务**: 每个请求完全独立，不需要上下文一致性。例如大规模文档分类、批量翻译等
- **成本极度敏感且质量要求宽松**: 比如内部工具的草稿生成，对输出质量要求不高
- **请求模式高度多样化**: 从简单问答到复杂推理混合在一起，且无法在设计时静态分类

### 什么场景不值得用

- **Agentic 工作流**: Agent 在执行多步任务时，模型切换会导致行为不一致、调试困难。Manifest 明确指出："管理那层额外的不确定性，成本可能超过节省的费用"
- **生产级应用**: 需要可靠的 evals、可观测性、可复现的调试。模型切换让所有这些工程实践变得复杂
- **需要缓存优化的场景**: 系统提示词和对话历史占大量 token 时，Prefix Cache 的降本效果远超路由
- **团队协作场景**: 团队成员需要理解并掌控所使用的工具。频繁切换模型让知识共享和最佳实践沉淀变得困难

### 迁移成本

如果你当前使用 LLM Router 方案，迁移到固定模型 + 缓存架构：

1. **评估现有请求模式**（1-2 天）：分析你的请求中有多少比例真正需要多模型路由
2. **选择主模型**（1 天）：基于你的核心场景选择单一主力模型
3. **启用 Prefix Cache**（半天）：大多数 LLM gateway 和代理层已支持缓存
4. **调整 system prompts**（1-3 天）：为固定模型优化提示词，替代之前为多模型设计的通用 prompts
5. **更新 evals 和监控**（1-2 天）：简化评估管线，移除多模型适配层

总工作量估计：3-8 人日，取决于现有系统复杂度。
