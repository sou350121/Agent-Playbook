## 是什么 / 解决什么问题

安全领域的 Agent 评测长期有个尴尬：**"找 bug 修 bug"这类任务，人工判分成本极高，而自动化判分又容易奖励"猜中了 patch 的形状"而不是"真的修好了漏洞"**。前一代 CWE-bench 已经验证了"真实开源仓库 + 程序化判分"这条路可行，但覆盖面偏窄，难以区分前沿模型的真实差异。

CWE-bench v2 的核心主张是三个词：**coverage、quality、transparency**（这是博客标题原话，也是文章自身的组织逻辑）。覆盖度上，100 个任务覆盖 91 种不同的 CWE，跨越很宽的漏洞类别。博客对此给了一个很直白的论证：防御方必须预判攻击者每一条可能的进入路径，而且每一次都要判断正确——因此一个只有在"见过同类模式"时才表现好的模型，在这个集合上会暴露短板。

质量层面，作者把每个任务的审查清单公开了（见下文「核心设计决策」），并强调**每个任务都经过人工复核**。透明度层面，公开集、判分器、harness 全部开放；同时保留一份 hold-out 集（`cwebench.com`，需通过邮件申请）用于追踪"没有任何模型见过"的任务上的进展。

## 技术架构拆解

### 核心设计决策

- **任务形态固定为"真实仓库 + 短指令 + 修一个弱点"**。Agent 拿到的是真实开源仓库的 checkout，以及一条"读起来像真实工程需求、而不像评测指令"的 instruction，目标是找出并修好安全弱点，同时不破坏既有功能。这是刻意的：任务越贴近工程现实，"刷榜技巧"的空间越小。
- **判分完全程序化，不引入 LLM 打分**。博客明确说 scoring is fully programmatic，因此结果确定、任何人都能零额外成本复现。LLM judge 面板的角色是**设计期**用来校准检查项，让它朝"更难、更公平"的方向走——而不是在评测期介入判分。
- **每条任务都自校验**。博客列出的六项检查（原文）：
  - 指令是否读起来像真实指令，而非评测设定？
  - 每一个被判分的行为，能否从指令中推导出来？
  - verifier 校验的是"行为正确"，而非"某一种修复的结构"？
  - 起始代码是否 fail、参考修复是否 pass？
  - 换成新修复后，原有功能是否仍然可用？
  - verifier 是否能挡掉**记忆化解答**（例如已知的上游 patch）？
- **任务即 Harbor task**。每个任务是一个自包含的 Harbor task：Docker 化环境 + 指令 + 确定性 verifier，数据集附带 `registry.json`，因此可以**不 clone 任何东西**直接从 Hub 跑整个基准。
- **同一套环境兼作 RL 训练环境**。任务被打了 `rl-environment` 标签，同一批环境与 verifier 既能评测也能为防御型 Agent 提供训练奖励——这是比"又一个榜单"更有价值的复用。

## 实用评估

### 什么场景值得用

- **安全 Agent 的能力边界评估**：想知道"我的安全 Agent 到底能不能修没见过类型的漏洞"，91 种 CWE 的分布比单一模式基准有区分度。
- **模型选型的成本决策**：官方数据里，DeepSeek V4.1 Flash 以 $0.04/rollout 达 57.0% pass@1；Claude Opus 5.5 多花约十个点、达 67.3% pass@1，成本 $1.83；Gemini 4 Argon 再进一步到 67.8% pass@1，成本 $3.92。三者构成帕累托前沿。这个成本/收益曲线对"要不要上贵模型"的判断比单一分数有用得多。
- **防御型 Agent 的 RL 训练**：`rl-environment` 标签意味着 verifier 可以直接当奖励函数，省掉自建环境的一大块工作。
- **基准复现与审计**：判分程序化 + 公开 grader，适合做内审或论文复现。

### 什么场景不值得用

- **长链路渗透测试评估**：任务是"单仓库、单指令、修一个弱点"，不覆盖侦察 → 横向 → 提权的多步攻击链。
- **超大企业代码库**：Harbor + Docker 化环境的形态对仓库规模有隐含约束，博客未说明任务仓库的规模分布——`> TODO: 主要任务对应的仓库 LOC / 依赖规模分布未在博客中给出`。
- **实时/生产环境的混淆风险**：公开集是公开的，模型供应商可能针对它做针对性优化；能说明真实进展的只有 hold-out 集，而 hold-out 需邮件申请，个人/小团队接入成本高。
- **把 pass@1 当绝对能力值**：官方自己也指出，即使榜首模型也"每次尝试都失败 19% 的集合"，说明长尾远未解决，单一分数不能外推。

### 迁移成本

- **从自建评测迁过来**：主要工作是把 Agent 接入 Harbor 的 `--agent` / `--model` 接口，并按需设置 `--allow-agent-host`。数据集有 gating，需要先在数据集页接受访问条件，并执行一次 `hf auth login --token $HF_TOKEN --add-to-git-credential`，因为 Harbor 用 git 拉取任务。按博客口径，这基本是"半小时级"的接入。
- **从旧 CWE-bench 迁过来**：任务定义形态不变，主要差异在覆盖面与判分严格度，历史分数不可跨版本直接比较。

## 对你的意义

如果你的关注点是 Agent 工程与评估工具链（而非安全本身），CWE-bench v2 有三点值得借鉴，且都被这个基准自身的实践支撑：

1. **"程序化判分 + LLM 只做设计期校准"是个可迁移的配方**。用 LLM 面板来打磨检查项、让判分更难更公平，但评测期不引入 LLM 打分——这解决了"LLM-as-judge 方差大、不可复现"的老问题，同时保留了 LLM 在规则设计上的效率。任何要建自有 benchmark 的场景都可以照抄这个分工。
2. **verifier 的六项自检清单可以直接搬**。尤其是"verifier 是否能挡掉记忆化解答"和"判分校验的是行为而非某一种实现结构"——这两条是绝大多数内部评测缺失的，也是最容易让评测失真成"复现已知 patch"的地方。
3. **同一套环境同时当评测与训练环境**（`rl-environment` 标签）是低成本复用做法；如果你的 Agent 评测集已经存在，检查一下它能否顺手产出训练奖励。

**建议**：如果你在评估 Agent 的代码能力，值得花一次 30 分钟把 CWE-bench v2 跑起来——不是为了分数，而是为了看它在"起始代码 fail / 参考修复 pass / 原功能不回归"这套三段式校验下，暴露你 Agent 的哪一类失败模式。安全领域之外的话，观望即可，直接抄它的 verifier 设计清单。

## 关键代码/配置片段

从 Hub 数据集直跑整个基准（引自官方博客，未改动）：

```bash
harbor run --repo "https://huggingface.co/datasets/collinear-ai/cwe-bench" -d cwe-bench@2.0 -k 4 \
  --agent <agent> --model <model> --env docker \
  --allow-agent-host <model API host>
```

博客对 `-k 4` 的说明：每个任务跑 4 次尝试，报告分数是全部 400 次试验的平均奖励。

数据集有 gating，且 Harbor 用 git 拉取任务，因此需要先登录一次：

```bash
hf auth login --token $HF_TOKEN --add-to-git-credential
```
