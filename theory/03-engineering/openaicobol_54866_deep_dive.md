## 是什么 / 解决什么问题

真正支撑全球关键基础设施的语言，往往不是模型训练语料里最多的那些。OpenAI 引用的事实很直白：COBOL 支撑超过 40% 的在线银行系统、80% 的线下信用卡交易与 95% 的 ATM 交易（来源：官方 blog 引述 IBM 资料）；Fortran 仍用于天气预报与核反应堆安全分析（来源：NOAA / NRC）。这些系统的共同困境是：文档不全、原始开发者退休离场、业务规则只以代码形式存在。

这正是 Agent 编程能力的一个「盲区悖论」——模型在 Python / JavaScript 上飞速进步，但恰恰在最需要自动化、最缺人力的地方最弱。OpenAI 在文中明确说，这一方向由开发者和企业客户的反馈驱动：编码模型在这些语言上常常失败。

这次不是新模型发布，而是一次**评测体系 + 能力数据**的公开：两套互补的评测，分别对应「建新软件」与「保住旧软件行为」。

## 技术架构拆解

### 核心设计决策

- **用「共享接口」做到跨语言可比**：MultiLangBench 的任务是在 20 种语言中从零实现一个 SQLite 兼容数据库引擎。为公平比较，评测不读代码、不看实现语言，而是把**数据库文件本身**当接口——给候选程序一个初始 db 文件 + 一条 SQL 查询，让它产出修改后的 db 文件，再用参考版 SQLite 校验内容。这一设计让「测试用例」与「实现语言」彻底解耦。
- **复用 SQLite 自有测试套件**：测试来自 SQLite 现有 test suite 的改编，而非新造题目，意在衡量「长会话中能积累多少可工作的功能」，而非单点题目正确率。
- **同时报告能力与成本**：结果不只给通过率，还给每次采样的 API 成本估算 —— 这是把编码 Agent 当工程决策而非排行榜看的态度。
- **迁移评测用「隐藏测试 + 字节级一致」**：COBOL 迁移到 C++ / Java / Kotlin / Python / Rust，全部隐藏测试通过才算成功，要求可观测输出 byte-for-byte parity。
- **刻意选择业务语义陷阱作为考察点**：文中点名 COBOL 定点算术在未显式声明 ROUNDED 时直接**截断**多余小数位。一个「能跑通」的重写如果改成四舍五入，程序不报错，财务结果却变了。这类题目只有真正理解语言语义的模型才能通过。

## 实用评估

### 什么场景值得用

- **遗留系统现代化的可行性预研**：先用模型对一批低风险 COBOL 模块做迁移，跑 byte-for-byte 回归，据此估算整体迁移的自动化比例与剩余人工工作量。相比「全部外包重写」，这是一次成本可控的摸底。
- **跨语言一致性组件**：需要在多种运行时（如 Rust 侧车 + Python 服务端）实现同一套逻辑时，MultiLangBench 这类任务形态与真实工作高度接近，模型产出可作为实现起点。
- **非主流语言的技术债清理**：Fortran 科学计算代码、VB 历史脚本的 21%~27% → 83%~89% 的跃升，意味着过去「模型帮不上」的代码库现在值得重新试一次。
- **成本敏感场景选 Luna**：GPT‑6 Luna 约 78% 的成本下降，但 MultiLangBench 通过率只有 40.3% —— 适合高频、低风险、可自动校验的子任务（如单函数改写、测试生成），不适合整体迁移。

### 什么场景不值得用

- **把 86.6% 当成「可以直接上线」**：官方自己写了边界——用于生产软件仍需专家 review，并针对业务规则与依赖做测试。迁移评测是隐藏测试集，与真实系统的完整性不可等同。
- **认为评测饱和就是问题解决**：COBOL 迁移评测在高推理预算下达到 97.9%，接近饱和。评测饱和通常意味着**评测开始失去区分度**，而非现实世界的迁移难题被解决。
- **把建库通过率当作生产可用率**：MultiLangBench 衡量的是「能实现多少 SQLite 功能」，不是「能写出生产级数据库引擎」。通过率 87% 不等于工程质量 87%。
- **指望它替代 COBOL 语义专家**：定点算术截断、缺记录处理这类细节才是迁移风险主源，模型越强越容易「写出看起来对但语义错」的代码，反而需要更强的专家回归把关。

### 迁移成本

- 从「无自动化迁移」切到「模型辅助迁移」：真正的成本不在模型调用（单样本不到 1 美元量级），而在于**搭建字节级回归基线**——你需要先把现有系统的可观测输出（报表、交易流水、边界输入）固化成可自动比对的测试集。这一步通常占总工作量的大头。
- 从 GPT‑5.6 切到新模型：若你已在做同类尝试，属于模型选型替换，改动在 prompt/推理预算配置上；`reasoning_effort` 从低到高带来的准确率跃升（86.6% → 97.9%）值得单独做成本/准确率曲线。

## 对你的意义

对做 **Agent + UI / RAG 工具链** 方向的团队，这篇的直接收益不是「去迁 COBOL」，而是三点方法论：

1. **评测设计可以照搬**。MultiLangBench 的「用共享产物（db 文件）做跨实现接口」是一个非常干净的可比性思路。你要评估一个 RAG 流水线或 Agent 工具链，与其比 prompt，不如定义一个**所有实现都必须产出的中间产物**，然后只校验该产物。这能让你自己的 eval 在多模型/多框架之间真正可比。
2. **「能力 vs 成本」双轴报告应该成为默认**。通过率 + 单样本成本一起报，才配得上叫工程评估。你的内部评测也该这么出表。
3. **COBOL 72% 这个异常值值得记住**。它说明：语料稀缺性是模型能力天花板里最难靠规模解决的一项。你的业务里如果有类似的「私有/低语料」子领域（内部 DSL、私有协议、特定领域的结构化输出），别指望通用模型自然覆盖，需要单独的 few-shot 或外挂知识。

建议：**观望 + 借用方法**。不必为 COBOL 迁移单独投入，但把 MultiLangBench 的评测思路和它公开在 GitHub 的测试套件拿来看一眼，对你自己的 Agent 质量体系有直接参考价值。
