## 是什么 / 解决什么问题

Vibe coding 这个词由 Andrej Karpathy 在 2025 年初提出，描述的是「你描述意图、AI 生成代码、你快速迭代」的工作方式。2025 到 2026 年，这套模式从个人玩具演变为企业工具链的默认形态：Copilot、Cursor、Claude Code、Codex CLI 几乎都采用「订阅 + 用量」的双轨计价，企业采购时也普遍把「默认开启 AI 补全」写进了工程规范。

问题在于，这套模式的**成本模型从来没有被认真审计过**。企业的思维是「人均每月固定费用」，实际账单却取决于 token 消耗量，而 token 消耗量与「AI 到底帮上了多少忙」之间没有线性关系。

这次微软的动作，本质上是一次**成本结构的证伪**：当 AI 成为每个工程师的标配副驾，企业要同时支付（1）工程师的工资、（2）AI 的 token 账单、（3）审查 AI 产出的额外工程时间。第三项最容易被忽略——AI 生成得越多，需要 review 的代码量越大，而 review 并不能像生成那样被加速。

据 36Kr 报道，微软在部分团队按下了暂停键，理由是 token 支出已超过员工成本的可比部分。这个数字本身需要谨慎对待（不同团队口径差异巨大），但它传递的方向是明确的：**vibe coding 的边际成本不是零**。

## 技术架构拆解

### 核心设计决策

这一节不讨论某个工具的架构，而是讨论**成本为何会失控的结构性原因**。Vibe coding 的成本失控不是计价问题，是工作流的结构问题：

- **生成成本远小于验证成本，但账单只记录生成成本**。LLM 生成 500 行代码的 token 费用可能只有几美分，但如果这 500 行里有 3 个隐蔽 bug，工程师花在定位与修复上的时间是 2 小时。企业的财务系统只看得见前者。
- **Agent 模式下 token 消耗呈非线性**。一个带工具调用的 coding agent，单次任务可能调用几十次模型、读取几十个文件、执行多轮修复循环。单看每次调用都很便宜，乘上循环次数就是另一回事。
- **上下文重复计费**。长对话、长仓库上下文、反复的失败重试，都会让同一份代码被反复计费。这是「延迟 + 成本」的双重放大。
- **订阅制掩盖了用量分布的长尾**。少数重度用户消耗了绝大多数 token，企业按人头付费时这部分成本被平均化；一旦改用 API 按量计价，长尾立刻暴露。

## 实用评估

### 什么场景值得用

- **陌生代码库的快速测绘图**：接手大型遗留系统时，让 agent 读完整套 crate / package 并生成调用图，这类任务一次性、高价值、产出可被人工快速验证。
- **机械但有判断的迁移**：如测试框架升级、API 签名批量替换、跨语言翻译。错误是局部且容易检测的。
- **有强测试护栏的重构**：测试覆盖足够时，agent 的快速迭代可以被自动化验证吸收，人工 review 成本显著下降。
- **一次性脚本与数据探查**：丢弃型代码，不对质量负责，只对结果负责。

### 什么场景不值得用

- **默认开启的全民补全**：低价值、高频率、采纳率却不高的场景，恰好是 token 浪费最严重的区域。
- **复杂业务逻辑的「一句话生成」**：错误不明显，review 成本高于自己写。
- **无测试覆盖的存量系统**：agent 的迭代循环没有自动化反馈，等于把所有验证压力转移到人身上。
- **成本极度敏感的早期团队**：按量计价下的长尾成本可能超过人力投入的等值。

### 迁移成本

从「全民 vibe coding」退回到「任务级使用」，主要成本不是技术迁移，而是**流程与文化的回退**：

| 动作 | 工作量 | 说明 |
|------|--------|------|
| 统计各团队实际 token 消耗 | 低 | 多数 API 网关已提供按用户 / 按项目的用量视图 |
| 把「AI 使用」从默认值改为选项 | 中 | 需要更新工程规范与 onboarding 文档 |
| 建立任务级 ROI 判断标准 | 中高 | 真正的难点：需要明确「什么任务值得开 agent」 |
| 为 review 增加 AI 产出标记 | 低 | diff 级别的 provenance 标记，便于针对性审查 |

## 对你的意义

如果你在跑 agent 相关的研究或工程，这件事的直接关联有三层：

1. **成本可观测性会成为 agent 框架的差异化功能**。目前多数框架对「一次任务总共花了多少 token、在哪个环节浪费最多」几乎没有可视化。这是一个明确的产品空缺——你之前关注的 AI Gateway 类工作（session affinity、缓存命中率）正是在填补这一层。
2. **「杠杆率」比「成功率」更重要**。Benchmark 上 agent 的成功率被反复比较，但企业真正关心的是「每美元换来多少合入主干的有效代码」。这个指标目前在公开研究里几乎是空白。
3. **小模型 + 窄工具的价值被重新定价**。当成本成为约束，MCP 式的窄工具搭配较小模型，可能比「大模型 + 通用 shell」在单位经济性上更优——这与 Simon Willison 近期对 stateless MCP 的重新拥抱形成了有趣的呼应。

**建议**：不必因为这条新闻调整方向，但值得在评估任何 agent 方案时，把「任务总 token 消耗」和「人工 review 工时」列入必测项。这两个数字目前几乎没人系统测量，先做的人会先看清真相。
